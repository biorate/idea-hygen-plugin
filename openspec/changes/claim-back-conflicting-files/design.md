# Design

## Context

Проверка 0.6.0 показала: пользователь не хочет снимать чужой паттерн `.env.*` (он нужен dotenv для настоящих env-файлов) и решил конфликт добавлением точного имени `.env.t` к нашему типу через UI — платформа резолвит exact-имена с приоритетом над glob (эмпирически подтверждено). claim-back — легитимный механизм (тот же, что использует UI File Types), не хак, при условиях: имена выводятся в рантайме (не хардкод), claim'ы управляемы (снимаются при исчезновении конфликта), всё по явному подтверждению.

## Goals / Non-Goals

**Goals:**
- Claim-back конфликтных файлов точными именами как первичный способ разрешения.
- Только реально существующие файлы (VFS), управляемый жизненный цикл claim'ов (persist + cleanup).
- Детекция перестаёт репортить файлы, уже резолвящиеся в наш тип.
- Resolve (снятие чужого паттерна) и suppress остаются как альтернативы.

**Non-Goals:**
- Генерация гипотетических имён под пересечение (только реальные файлы).
- Гарантии приоритета среди конкурирующих exact-имён разных типов (спайк + документирование, не решение).
- Захват файлов, не подходящих под настроенные паттерны пользователя.

## Decisions

1. **Поиск конфликтных файлов — VFS-обход по корням контента проектов.** Для каждой пары (наш паттерн × чужой паттерн) ищем файлы, чьи имена соответствуют обоим (переиспользуем `GlobMatcher`), по `ProjectManager.getInstance().openProjects` → content roots; глубина ограничена сравнением имён, без рекурсивного чтения контента. Кап на количество предлагаемых имён в одном диалоге (например, 20) — от взрыва на патологичных пересечениях. Замечание: `.env.t` в `_templates/` найдётся, поскольку корпуса лежат в content roots открытых проектов.
2. **Добавление claim'а — публичный API.** `FileTypeManager.associatePattern(HygenFileType, exactName)` — точное имя (без `*`) регистрируется тем же механизмом, что и наши текущие паттерны; IDEA хранит его в `filetypes.xml` (переживает рестарт). Проверка «exact бьёт glob» — спайк-задача §1 (в т.ч. краевой случай: чужой тип с тем же exact-именем — задокументировать наблюдаемое поведение, решение не гарантировать).
3. **Учёт claim'ов в детекции.** Перед резолвом представительного имени детектор дополнительно проверяет реальные конфликтные файлы: если файл резолвится в наш тип (уже claim'нут) — конфликт для этой пары не репортится. Это закрывает и «ложный репорт после ручной правки» из 0.6.0. Проверка реальных файлов стоит VFS-обхода — выполнять только когда пересечение паттернов непусто и детектор уже нашёл потенциальный конфликт.
4. **Claim-менеджер — отдельный класс** (`FileTypeClaimManager`): persistent state (application-level, рядом с `HygenFileTypeConflictSettings`, ключ — exact-имя), API `claim(name)`, `release(name)`, `claimed(): Set<String>`. Cleanup на каждом sync: для каждого claim'а — файл ещё существует И имя всё ещё попадает под настроенный наш паттерн, иначе `release`. Снятие через `FileTypeManager.removeAssociation` (публичный, уже используется 0.6.0). Никогда не трогаем exact-имена, добавленные не нами (нет в нашем state).
5. **Диалог/notification.** В агрегированном балуне конфликт с существующими файлами получает действие «Claim back N file(s)…», открывающее список с чекбоксами + кнопки «Claim back» / «Remove foreign pattern» / «Cancel»; suppress-действие остаётся на балуне. Всё — только по явному подтверждению.
6. **Точка интеграции** — та же: хвост `HygenTemplatePatternsLifecycle` после sync; claim-менеджер вызывается до детекции (cleanup), затем детекция с учётом claim'ов. Тесты — на seam'ах (probe/foreign patterns/remover уже есть; добавляется seam точных ассоциаций и фейковый VFS-список файлов).

## Risks / Trade-offs

- Приоритет exact-vs-exact не документирован — спайк, при негативном результате claim-back всё равно работает для нашего кейса (glob-vs-exact подтверждён), риск задокументирован в README.
- VFS-обход на больших проектах — ограничиваем сравнением имён файлов в известных корнях + кап; обход ленивый (только при найденном пересечении паттернов).
- Пользователь может claim'нуть файл, который реально хочет отдать dotenv — действие всегда ручное, подтверждение через список; снятие через cleanup или вручную (Settings).
- Откат безопасен: фича аддитивна; при отключении хука claim'ы остаются валидными exact-ассоциациями платформы.
